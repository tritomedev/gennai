# 源内の価値と限界：正直な整理

- **作成日:** 2026-07-08
- **ステータス:** 完了
- **重要度:** ★★★（サービス展開を検討する上での核心）

---

## 源内の本質：AIではなくインターフェース

**源内はAIではない。AIを束ねて使いやすくする基盤（オーケストレーター）。**

```
よくある誤解：源内 ＝ AI
正確な理解：源内 ＝ AIを束ねて使いやすくする基盤
```

### 源内の役割

| 役割 | 具体的に何をしてるか |
|---|---|
| **インターフェース** | ユーザーとAIの間に立つUI・API |
| **オーケストレーター** | 複数のAIアプリ・LLMを束ねて管理 |
| **セキュリティレイヤー** | 機密情報を守りながらLLMを呼び出す |
| **プラットフォーム** | 誰でもAIアプリを追加・管理できる仕組み |

AIそのものもLLMも持っていない。**「AIを安全に・簡単に使える環境」を提供しているのが源内**。

### スマートフォンのアナロジー

```
源内  ＝ スマートフォン本体
LLM   ＝ アプリ（LINE・地図・カメラ等）
```

スマホ自体はコミュニケーションツールではないが、LINEを入れたらコミュニケーションツールになる。
源内も同じで、LLMやRAGアプリを入れて初めて「AIシステム」として機能する。

---

## 源内は「LLM非搭載」＝「AI機能欠落」ではない

源内単体では文章を1文字も生成できない（LLM本体を持たないため）。この意味では「AI機能非搭載」は正しい。

しかし、LLM単体でも実現できない機能を源内側が担っている。

```
LLM単体      ＝ 賢いが何も知らず何も持っていない頭脳
源内のAIアプリ ＝ 頭脳に以下を与える仕組み
  ・業務知識（RAG・データベース連携）
  ・手順（プロンプト設計・ワークフロー）
  ・道具（ファイル処理・外部システム連携）
  ・安全網（ガバクラ内で完結・権限管理）
```

例：Lawsy（法令RAG）にLLMを繋いだとき、「法令を正確に引用して回答する」という機能はLLM単体にもLawsy単体にも存在しない。**組み合わせて初めて生まれる機能**。

**正しい表現：**
- ❌ 源内はLLM非搭載なのでAI機能が欠落している
- ⭕ 源内はLLM非搭載だが、**AIを業務で使える形にする機能**は源内側が担っている

### スマホのアナロジー（続き）

源内は「SIMカードが入っていないスマホ」に近い。通信（＝生成能力）はできないが、カメラアプリ・UI・連絡先管理という価値の大部分はスマホ側に実装されている。SIMを挿した瞬間（＝LLMを繋いだ瞬間）にすべてが機能し始める。

---

## 源内は「対話型」より「処理型」が主戦場

源内で提供されるAIアプリ一覧（2026年2月20日時点）を分析すると、実は**チャットで自由に会話するアプリより、フォーム入力→定型処理→結果出力という「処理型」アプリのほうが多い**。

参照: [源内で提供されるAIアプリ一覧（PDF）](https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/cef0122b-0598-47f8-8a48-dc2c57d407c1/875e8cce/20260324_policies_gennai_table_01.pdf)

### 対話型 vs 処理型の分類

| 対話型（チャットで会話） | 処理型（RPA的：入力→処理→結果） |
|---|---|
| チャット | 神エクセル変換 |
| 目標設定チェッカー | マークダウン表変換 |
| 文章を生成 | Excel関数の提案 |
| | ALT（代替テキスト）作成 |
| | 音声文字起こし |
| | パブコメ分類AI |
| | 文章を校正・添削（ファイル添付版） |
| | SEABIS質問応答RAG |
| | 物品管理システム質問応答RAG |
| | 補助金制度調査（jGrants） |

### なぜ処理型が多いのか：API仕様に理由がある

[AIアプリAPI仕様](../02_research/ai-app-api-spec.md)を思い出すと理由がわかる。
`text` `file` `select` `checkbox` 等のUIコンポーネントで入力フォームを組み立てる仕様になっており、これは**チャットボットのUIではなく業務システムの入力フォームのUI**そのもの。

```
一般的なAIチャット ＝ 自由テキストで壁打ち
源内のAIアプリ    ＝ フォームに入力 → ボタンを押す → 結果が返る
```

### 使用LLM（参考）

源内のチャットアプリでは複数LLMを切り替えて利用できる設計になっている。

- Claude Sonnet 4.6
- Claude Sonnet 4.5
- Claude Haiku 4.5
- Nova Lite

翻訳アプリでは国産LLM「PLaMo翻訳（Preferred Networks社）」を使用しており、**処理がガバメントクラウド環境内で完結し入力情報が外部送信されない**点が明記されている。これが国産LLM導入の主要な動機になっている。

## 図書館ユースケースへの示唆（追加）

源内の設計思想が「処理型」中心であることを踏まえると、図書館蔵書AIも**チャットで壁打ちする形より、フォーム入力→レポート出力という形**が源内の思想に合っている。

```
入力フォーム例：
- テーマ・キーワード（text）
- ジャンル（select: 小説 / 実用書 / 専門書）
- 対象年齢（select）
    ↓
出力：おすすめ蔵書リスト＋要約レポート
```

また、既存の「SEABIS質問応答RAG」「物品管理システム質問応答RAG」は**庁内システムへの問い合わせをRAG化したアプリ**であり、これは「蔵書データへの問い合わせをRAG化する」図書館ユースケースと構造が完全に一致する。既存実装が有力な参考になる。

## 結論から言うと

源内は「LLMさえ用意すれば、あとの面倒なインフラを全部飛ばして業務AIアプリを作れる基盤」。
LLM本体は含まないため、**LLMの調達・コスト設計は常に別途必要になる**。

---

## Q1. LLMは個別に調達が必要か？

**YES、必要。**

源内はLLMを「呼び出す基盤」であってLLM本体は含まない。
現在の源内はAzure OpenAI（GPT-4系）やGeminiを外部から呼び出している。

### 選択肢

| 選択肢 | コスト | セキュリティ | 向いているケース |
|---|---|---|---|
| Azure OpenAI / Gemini | 従量課金 | APIにデータ送信 | 手軽に始めたい |
| 国内LLM（tsuzumi等） | 調達が必要 | 国内データセンター | 行政・機密情報を扱う |
| Ollama（ローカル） | ほぼ無料 | 完全ローカル | Proxmox等の自前環境 |

### 図書館ユースケースでの現実解

**Ollama + ローカルLLM** が最も現実的。
- 個人情報を含まない
- 外部送信リスクがない
- コストがほぼかからない

## Q2. RAGアプリを作るのは難しいか？

**実装自体は難しくない。難しいのはデータ整備。**

```
実装の難しさ：  ★☆☆（最小実装は数十行）
データ整備の難しさ：★★★（ここが本番）
```

### 実装はシンプル

```python
@app.post("/")
def search(req: dict):
    docs = vector_search(req["inputs"]["input_text"])
    answer = llm.generate(question, context=docs)
    return {"outputs": answer}
```

### データ整備が本番

- 古いPDF・スキャン画像のOCR精度問題
- チャンクの切り方で回答品質が大きく変わる
- メタデータ（タイトル・著者・ページ）の整備
- 定期的な更新・同期フロー

**「コードより蔵書データをどう整備するかが肝」**

## 源内の本質的な価値と限界

### 電気と家電のアナロジー

```
LLM     ＝ 電気（なければ何も動かない・別途調達が必要）
源内    ＝ 家電一式（電気さえあれば即使える・一から作らなくていい）
```

源内があることで「LLMを繋ぐだけで業務AIが動く状態」になる。
LLMなしでゼロから全部作るよりはるかに速い。

### 限界・課題

| 課題 | 内容 |
|---|---|
| **LLMコスト** | 従量課金の外部LLMを使う場合、利用量に比例してコストが増える |
| **AWS依存** | genai-webはAWS前提の構成。他環境への移植コストが高い |
| **完全ローカル不可** | genai-web単体では完全ローカル動作ができない |
| **LLM品質の依存** | 源内の回答品質はLLM次第 |

## サービス展開時のLLMコスト設計が重要

源内を使ったサービスを**他者に提供する**場合、LLMコストをどう設計するかが事業の核心になる。

### パターン比較

| パターン | LLM | コスト負担 | 向いているケース |
|---|---|---|---|
| **SaaS型** | 外部LLM（API） | 提供者が負担 or 従量請求 | 手軽に展開したいとき |
| **オンプレ型** | ローカルLLM（Ollama等） | 初期ハードウェア投資のみ | セキュリティ重視・大量利用 |
| **ハイブリッド型** | 用途に応じて使い分け | 混在 | 高精度と低コストを両立 |

### 図書館ユースケースでの推奨

**オンプレ型**が最適。
- 市民の検索内容を外部送信しない（プライバシー）
- 利用量が増えてもコストが増えない
- 図書館サーバーにOllamaを置くだけで動く
