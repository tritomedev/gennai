## TASK-004：源内Web内蔵チャットのLLM接続は自作アプリと共有できるか

### 結論：できない（実機検証により確定）

DevelopersIOの検証記事により、以前の推測が裏付けられた。

> ExAppの API は `{"inputs": {...}}` を受け取り `{"outputs": "..."}` を返す REST API のプロトコルに準拠する必要がある。「API リクエストのデータ形式」には、源内の UI に自動生成するフォームの定義を JSON で記述する。

さらに決定的なのは通信経路の説明：

> 源内 Web から ExApp を呼び出す際は、源内 Web のバックエンド Lambda が VPC 内から NAT Gateway 経由でこの API Gateway にリクエストを送る。API Gateway の手前には WAF がホワイトリスト方式で配置されており、源内 Web の NAT Gateway Elastic IP のみ許可する構成である。

つまり：

- ExApp（自作AIアプリ）は**API Gateway + 自前のAPIキー**を持つ完全に独立したシステム
- 源内Webは単に「許可されたIPからのリクエスト」としてExAppを呼び出すだけ
- 源内Web内蔵チャットが使うLLM接続（Bedrock等）とExApp用のLLM接続には**一切の共有機構がない**
- ExApp側でLLMを呼び出す場合、**自分でBedrock/Azure OpenAI/Gemini等と契約し、自分のAPIキーで呼び出す必要がある**

### ExAppでできること・できないこと（実機検証より判明）

> できること: 8種類のフォームコンポーネント（text / number / textarea / select / radio / checkbox / file / hidden）を組み合わせた入力画面の自動生成。REST APIであればクラウドや言語を問わず登録可能。`outputs`にMarkdownを返すことでリッチな結果表示。ファイルのアップロード（Base64エンコードで送信）。`artifacts`でファイル（画像等）を返すことも可能。

> できないこと: チャット形式のインタラクティブなやり取り（1ショットのリクエスト/レスポンスのみ）。ストリーミングレスポンス。フォームのレイアウトやデザインのカスタマイズ（フィールドは縦に並ぶ固定レイアウト）。

これは以前整理した「対話型 vs 処理型」の議論を裏付ける実証結果。チャットのようなインタラクティブな機能は源内Webの汎用AI側で提供されていて、ExAppは「特定の業務に特化したAPIをGUIから呼び出す」ための仕組みという位置づけ。

### コスト面への影響（実機検証で判明した試算）

| 構成 | 月額固定費目安 | 主要コスト |
|---|---|---|
| 源内Webのみ | 約$20〜30 | WAF（WebACL×3）が大半 |
| 源内Web + クエリ拡張RAG 1つ | 約$200〜390 | OpenSearch Serverlessが大半 |
| 源内Web + カスタムAPI（Lambda + APIGW） | 約$20〜30 | ExApp自体の追加コストはほぼゼロ |

**重要な気づき：** Lambda + API Gatewayだけのシンプルな構成なら追加コストはほぼゼロ。ベクトル検索基盤（OpenSearch Serverless等）がコストの大半を占める。これはOllama＋ローカルベクトルDBでのセルフホスト構成の優位性を裏付ける材料になる。

## TASK-019：Lawsy公式READMEの直接確認（代替確認）

### 結論：GitHub直接アクセスは引き続き不可。ただし実機検証記事で3テンプレートの構成が判明

Lawsy自体のREADME直接取得はGitHubのbot制限により不可のままだが、3つのAIアプリテンプレートの内部構成が実機検証で判明した。

| クラウド | テンプレート | 概要 |
|---|---|---|
| AWS | クエリ拡張RAG | Bedrock Knowledge Base + OpenSearch Serverlessを使ったRAG API |
| Azure | vLLMセルフデプロイ | PLaMo翻訳モデルをVMSS上のvLLMでホスティング + Azure OpenAI |
| GCP | 法制度AIアプリ（Lawsy） | BigQuery MLベクトル検索 + Geminiで法令レポートを生成 |

### AWS版（クエリ拡張RAG）の詳細構成が判明

> API Gatewayが外部からのリクエストを受け付け、x-api-keyヘッダーで認証。RAG Lambda（Python）がクエリ拡張→Knowledge Base検索→関連性評価→回答生成の一連の処理を実行。Bedrock Knowledge BaseがOpenSearch Serverlessをバックエンドにドキュメントをベクトル検索する。

使用モデル（デフォルト）：
> デフォルトでは回答生成にClaude Haiku 4.5、クエリ拡張・検索生成・関連性評価にNova 2 Liteが使われる。`config/apps/qerag.toml`でデフォルト設定から変更したい項目だけを記述する仕組み。

これは図書館蔵書RAGの設計における重要な参考パターン：
- **軽量モデル（Nova Lite等）を前処理・評価に使い、高性能モデル（Claude Haiku等）を最終回答生成に使う**という段階的モデル使い分けが、コスト最適化の定石として使われている

### 図書館ユースケースへの示唆

Lawsy（GCP版）はBigQuery、AWS版はOpenSearch Serverlessと、いずれもマネージドサービス依存。
**Proxmoxでのセルフホストを目指すなら、この2つのテンプレートよりも「TOMLで設定を切り替える設計」「クエリ拡張→検索→関連性評価→生成という多段パイプライン」という設計思想を参考にしつつ、バックエンドをpgvector/Qdrant + Ollamaに置き換えるのが現実的。**

## TASK-020：tsuzumi 2のオンプレ版の料金・調達方法

### 結論：個人向け提供なし。法人・公共機関向けの個別商談制、価格非公開

複数の情報源から共通して確認された内容：

**提供形態**
> tsuzumi 2は法人・公共機関専用のB2Bモデルで、公開価格表はない。導入はNTTデータ、NTTドコモビジネス、NTT東日本ビジネスイノベーションなど、NTTグループ各社経由の個別商談ベースとなる。

**技術的特徴（オンプレ適性）**
> tsuzumiはNTTがフルスクラッチでゼロから開発した純国産モデル。1GPUで動作可能な軽量モデルでコストパフォーマンスに優れている。低コストでオンプレミスやプライベートクラウドでの運用が可能であり、機密性の高い情報も安全に取り扱える。

**Azure提供ルート（法人向けの一つの選択肢）**
> Microsoft Azureにてtsuzumi 2を提供。Microsoft Foundryとの統合により、セキュアかつスピーディな導入が実現可能。モデル専用の計算リソースを確保して利用するマネージドコンピューティングを採用しているため、トークン量を気にすることなく安定したスループットを維持できる。
> 利用料金やサービスの詳細情報はMicrosoftのマーケットプレイス上のカタログ情報および利用マニュアルを参照する必要がある。

**中小企業向けの動き（オンプレ導入の入り口）**
> 2026年4月20日、INTELLILINK Private AI スタートパックでtsuzumi 2の対応検証を開始。中堅・中小企業がオンプレミスでプライベートAI環境を立ち上げる際のスタートキットとして提供される見込み。

### 個人・小規模プロジェクトでの現実的な結論

**tsuzumi 2は「個人・小規模開発者が気軽に試せるLLM」ではない。**

- 個人向け無料サービスなし
- 価格非公開・法人商談ベース
- 導入は基本的に企業単位（自治体・大学・企業）

図書館ユースケースのような**個人〜小規模開発の検証段階では、tsuzumi 2は選択肢から外れる**。国産・オンプレという条件を満たしたいなら、現実的には引き続き**Ollama + Qwen2.5 / Llama 3.1**が唯一の実践的選択肢。

tsuzumi 2は「将来、図書館システムが自治体単位で本格導入される段階」になったときに初めて検討テーブルに乗る選択肢、という位置づけが適切。
